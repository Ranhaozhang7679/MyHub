IDLE 状态切换与自动运行 — 风险分析报告

报告日期：2026-05-08  |  分析对象：Luster Motion 2026  |  关联问题：手动状态启动 IO 仍能运行  |  分析人：Claude Code

1. 分析背景

在修复「手动状态下启动 IO 仍能运行」问题（方案 A + C）后，进一步分析 EngineStatus.Idle 状态的切换逻辑，评估是否存在通过向 IDLE 状态切换或从 IDLE 状态出发导致非预期自动运行的路径。

分析范围：

  • 哪些场景会导致机台进入 IDLE 状态
  • 进入 IDLE 后 MachineMonitor 的 100ms 轮询会响应哪些 IO 信号
  • 从 IDLE 出发到 Running 的完整链路中是否存在安全薄弱点
  • 相邻状态（Ready/Alarm）的恢复路径是否存在绕过 IDLE 直接自动运行的风险

2. 状态机概览

Idle(0) ───── 默认值 ──────→ 初始状态（MotionEngine == null 时也返回 Idle）
Idle(0) ── Home() ──→ Homing(1) ── 回零完成 ──→ Ready(2)
Ready(2) ── Start() ──→ Running(4)
Running(4) ── 报警/暂停 ──→ Alarm(8) / Pause(16)
Alarm(8) ── Reset() ──→ Resetting(64) ── 复位完成 ──→ EStatus 决定目标
              ├─ EStatus == Ready → Ready(2) ← ⚠ 可直接被 StartButton IO 触发启动
              ├─ EStatus == Idle → Idle(0) ← 安全，需重新回零
              └─ 其他 → Pause(16)
Running(4) / 其他 ── Stop() ──→ Stop(32) （不会到 Idle）

注：EngineStatus 带 [Flags] 特性，Idle = 0 是默认值。MaterialPending(128) 仅用于界面显示，不参与状态切换。

4. IDLE 状态下 MachineMonitor 的 IO 响应

MachineMonitor() 每 100ms 轮询一次。以下列出 当 MachineStatus == Idle 时会执行的 IO 处理：

4.1 急停检测（始终执行）

// MotionController.cs:1840-1886
ProcessIO(SysConfig.EmergencyButton, io => {
    if (!io.GetDigitalIn())  // 急停常闭，false = 被按下
    {
        IsEmg = true;
        MotionEngine.OnAlarm(...);  // 触发急停报警
    }
});

无状态限制，任何状态下急停均有效。✓ 设计合理。

4.2 回零按钮（仅 IDLE/Stop）

// MotionController.cs:1890-1911
if (MachineStatus == EngineStatus.Idle || MachineStatus == EngineStatus.Stop)
{
    ProcessIO(SysConfig.RecoveryButton, io =>
    {
        if (io.GetDigitalIn())
        {
            homeTime += 100;
            if (homeTime > 3000)  // 持续按住 3 秒
                Home();  // → Idle → Homing → Ready
        }
    });
}

IDLE 下按住复位按钮 3 秒触发回零。回零完成后进入 Ready 状态，但不会自动运行。

4.3 复位按钮 — 报警清除（无状态限制）

// MotionController.cs:1913-1922
// ⚠ 没有任何状态判断！
ProcessIO(SysConfig.RecoveryButton, io =>
{
    if (io.GetDigitalIn())
    {
        Recovery();  // ← 任何状态都会调用
    }
});

在 IDLE 状态下按下复位按钮会调用 Recovery()，但 Recovery() 在 [line 1249](MotionController.cs:1249) 有保护：

// MotionController.cs:1249
if (MachineStatus != EngineStatus.Alarm) return;  // ← 非报警状态直接返回

但有副作用：在 return 之前已执行了关闭蜂鸣器（line 1240）和安全门检查（line 1235）。

4.4 启动按钮 — 报警忽略（IDLE/Alarm）

// MotionController.cs:1924-1954
if (MachineStatus == EngineStatus.Alarm || MachineStatus == EngineStatus.Idle)
{
    ProcessIO(SysConfig.StartButton, io =>
    {
        if (io.GetDigitalIn() && AlarmInfo != null &&
            (AlarmType.InfoTip | WarningTip | PlcAlarm))
        {
            ignoreTime += 100;
            if (ignoreTime > 3000)
                Recovery();  // ← IDLE 下 AlarmInfo 残留时可能触发
        }
    });
}

触发条件：AlarmInfo != null 且为特定报警类型，StartButton 持续按住 3 秒。

4.5 手动/自动切换（始终执行）

// MotionController.cs:1782-1823
ProcessIO(SysConfig.ManualSwitchButton, io =>
{
    var canRun = io.GetDigitalIn();
    if (isAutoMode != canRun)
    {
        CanAutoRunEvent?.Invoke(canRun);
        if (!canRun && MachineStatus != EngineStatus.Alarm)
            MachineManualEvent?.Invoke("Manual");  // 切到手动时触发暂停
    }
    isAutoMode = canRun;
});

在 IDLE 状态下，切到手动会触发 MachineManualEvent，最终调用 Pause()。但 Pause() 在 IDLE 状态直接返回（line 1392）。

5. 风险场景详细分析

风险 1：IDLE 状态直接触发自动运行

无风险

MachineMonitor 中 StartButton 的自动启动逻辑（line 1729-1755）仅在 Ready 或 Pause 状态下执行。IDLE 状态不存在直接自动运行的路径。

IDLE 状态下 StartButton IO 检测
↓
MachineMonitor line 1729: status != Ready/Pause → 跳过
↓
✓ 不会触发自动运行

风险 2：IDLE → Home → Ready → StartButton IO 链路

低风险

链路：

IDLE
↓ RecoveryButton 按住 3s
Home() → Homing
↓ 回零完成
Ready
↓ StartButton IO 检测到信号
CanAutoRun() 检查
↓ 如果通过
MachineStartEvent → tryStart → Running

风险条件（需同时满足）：

  1. 操作员按住 RecoveryButton 3 秒触发回零
  2. 回零完成瞬间 StartButton IO 信号恰好处于按下/抖动状态
  3. CanAutoRun() 返回 true（手动/自动 IO 误读或未配置）

现有防护：

  • ✓ 方案 A：CanAutoRun 安全默认值已修复（isAuto 默认 false）
  • ✓ 方案 C：MController_MachineStartEvent 独立检查已添加
  • ✓ Start() 方法入口（line 830）再次检查 CanAutoRun

风险 3：AlarmInfo 残留导致 IDLE 下 Recovery() 被意外调用

低风险

场景：报警恢复后 AlarmInfo 未被完全清理（clearAlarm() 竞态），IDLE 状态下按住 StartButton 3 秒触发 Recovery()。

// 触发路径：MachineMonitor line 1929-1940
if (io.GetDigitalIn() && AlarmInfo != null ...)  // ← 残留的 AlarmInfo
{
    ignoreTime += 100;
    if (ignoreTime > 3000)
        Recovery();  // ← 调用 Recovery
}

Recovery() 在 IDLE 状态的执行路径：

Recovery() 被调用
↓
lockCommand > 0 ? → 返回（防止连续调用）
↓
DoorIsClosed() 检查 → 可能抛异常
↓
SetBuzzer(false) → 关闭蜂鸣器 ⚠
↓
MachineStatus != Alarm → return（line 1249）

副作用：

  • ⚠ 蜂鸣器被关闭 — 可能掩盖正在进行的报警提示
  • ⚠ 安全门检查 — 门未关时抛出 FriendlyException，可能弹出错误提示框干扰操作
  • ✓ 不会导致自动运行 — Recovery() 在非 Alarm 状态直接返回

⚠ 风险 4（关联发现）：EStatus == Ready 的报警恢复路径

中高风险 — 不经过 IDLE，但与本分析高度相关

这是真正值得关注的路径：报警恢复后直接进入 Ready，跳过了 IDLE 的安全缓冲。

Ready 状态
↓ 报警发生
alarmInfo.EStatus = Ready（line 492）
↓ 报警 → Alarm
操作员按下复位按钮
↓ Reset
Resetting → EStatus==Ready → Ready（line 701）
↓ MachineMonitor 立即响应
StartButton IO 检测 + CanAutoRun → MachineStartEvent
↓
tryStart() → Start() → Running

风险链路详解：

  1. 机台处于 Ready 状态时发生报警 → EStatus 记录为 Ready（MotionController.cs:492）
  2. 操作员按下复位按钮清除报警 → MotionEngine.Reset() 执行（MotionEngine_part2.cs:632）
  3. 复位成功后，因 alarmInfo.EStatus == Ready，引擎状态直接设为 Ready（MotionEngine_part2.cs:701）
  4. MachineMonitor 的下一次 100ms 轮询检测到 Ready 状态（MotionController.cs:1729）
  5. 若 StartButton IO 处于按下/抖动状态 → 触发 CanAutoRun() 检查
  6. 若 CanAutoRun() 通过 → MachineStartEvent → tryStart() → 自动运行

时间窗口：从 Reset 完成（Ready）到 MachineMonitor 下一次轮询，最多 100ms。如果此时 StartButton IO 恰好处于高电平（操作员手未松开、信号抖动），就会被捕获。

现有防护：

  • ✓ 方案 A：CanAutoRun 安全默认值（isAuto 默认 false，需 IO 回调确认才能放行）
  • ✓ 方案 C：MController_MachineStartEvent 独立 CanAutoRun 检查
  • ✓ Start() 方法入口三重检查

剩余风险：三重 CanAutoRun 检查依赖同一个 ManualSwitchButton IO 读取。如果该 IO 本身存在信号抖动或误读，三重检查可能全部失效。

风险 5：RecoveryButton 无状态检查的副作用

低风险

// MotionController.cs:1913-1922
// ⚠ 此段代码没有状态判断，任何状态下 RecoveryButton 按下都会调用 Recovery()
ProcessIO(SysConfig.RecoveryButton, io =>
{
    if (io.GetDigitalIn())
        Recovery();  // 无前置状态检查
});

在 IDLE 状态下每次按下复位按钮都会执行：

  • DoorIsClosed() 检查（可能抛异常）
  • SetBuzzer(false) 关闭蜂鸣器
  • MachineStatus != Alarm → return 直接返回

不会导致自动运行，但存在不必要的安全门检查和蜂鸣器操作。

6. 风险等级汇总

风险场景 等级 现有防护 建议
IDLE 状态直接自动运行 无 MachineMonitor 不响应 —
IDLE → Home → Ready → StartButton 低 方案 A + C + Start() 三重检查 可考虑 Home 完成后增加延时再允许 Start
AlarmInfo 残留 → IDLE 下 Recovery() 低 Recovery() 非 Alarm 状态返回 清理 Recovery() 副作用（蜂鸣器、安全门检查移到状态检查之后）
Alarm(Ready) → Reset → Ready → 自动运行 中高 方案 A + C 建议 Reset 完成后不直接回 Ready，而是回 Idle 需重新确认
RecoveryButton 无状态检查副作用 低 Recovery() 状态检查保护 建议添加状态判断前置条件

防护弱点：第 2/3/4 层均调用同一个 CanAutoRun() 方法，读取同一个 ManualSwitchButton IO。如果该 IO 信号本身存在问题（抖动、误读、未配置），三重检查可能同时失效。

8. 结论与建议

结论：IDLE 状态本身是安全的，不会直接导致自动运行。

所有从 IDLE 到 Running 的路径都需要经过 Home() → Ready → Start，且每一步都需要明确的用户操作（按住按钮 3 秒、点击启动）。

真正的风险点在报警恢复路径：当 EStatus == Ready 时，复位完成后直接回到 Ready 状态，MachineMonitor 的 100ms 轮询会立即响应 StartButton IO 信号。方案 A + C 已覆盖此场景的三重检查，但均依赖同一个 IO 读取。

建议优化项（优先级排序）

建议 1（中优先级）：调整 Recovery() 副作用顺序

将 SetBuzzer(false) 和 DoorIsClosed() 移到 MachineStatus != Alarm 检查之后，避免在非报警状态下产生副作用：

public void Recovery()
{
    // 先检查状态，避免非报警状态的副作用
    if (MachineStatus != EngineStatus.Alarm) return;

    if (lockCommand > 0) return;
    if (!DoorIsClosed(out var errMsg))
        throw new FriendlyException(errMsg);

    _lightManager.SetBuzzer(false);
    // ... 后续逻辑
}

建议 2（低优先级）：RecoveryButton 报警清除添加状态前置判断

在 line 1913 处增加状态条件，避免在 IDLE 等无效状态下调用 Recovery()：

if (MachineStatus == EngineStatus.Alarm)  // ← 添加前置条件
{
    ProcessIO(SysConfig.RecoveryButton, io =>
    {
        if (io.GetDigitalIn())
            Recovery();
    });
}

建议 3（长期考虑）：评估报警恢复后目标状态策略

当前 EStatus == Ready 时复位后直接回到 Ready，可被 IO 信号立即触发启动。考虑是否需要：

  • 复位完成后统一回到 Idle，要求操作员重新回零确认后再启动
  • 或在复位完成 → Ready 转换时增加一个"冷却期"（如 2 秒内不响应 StartButton IO）
  • 或在 Reset 回调中增加一次独立的 CanAutoRun() 检查作为前置条件

此项需要评估对生产效率的影响，因为操作员可能期望报警恢复后快速恢复运行。
