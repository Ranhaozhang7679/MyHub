手动状态下启动 IO 仍能运行 — 问题分析报告

报告日期：2026-04-26  |  分析对象：Luster Motion 2026  |  分析人：Claude Code

1. 问题描述

现象：设备已切换到手动状态，按下启动 IO 按钮后，设备竟然正常启动运行。

预期：手动状态下，启动 IO 应被拦截，不允许自动运行。

风险等级： CRITICAL — 安全事故隐患

4. CanAutoRun 核心逻辑分析

// MotionController.cs:1055-1073
public bool CanAutoRun(out string mesage)
{
    bool isAuto = true;           // ← 默认值 true
    string error = "";
    mesage = "";

    ProcessIO(SysConfig.ManualSwitchButton, (r) =>
    {
        isAuto = r.GetDigitalIn();

        if (!isAuto)
        {
            error = "机台处于手动状态,不允许自动运行!";
        }
    });

    mesage = error;
    return isAuto;
}
// ProcessIO 实现 — MotionController.cs:1593-1607
private void ProcessIO(VDevice vDevice, Action<VIO> ioAction)
{
    if (vDevice != null && !vDevice.IsEmpty())  // ← 条件不满足时回调不执行
    {
        var io = vDevice.GetVDevice<VIO>(_deviceEngine);
        ioAction(io);
    }
}

5. 可能原因分析（按可能性排序）

原因 1：CanAutoRun 默认值 true 导致安全检查被静默绕过

可能性：高

isAuto 初始值为 true。当 ProcessIO 回调未执行时（ManualSwitchButton 为 null 或 IsEmpty()），isAuto 保持 true 不变，方法直接返回允许运行。

触发条件：

  • SysConfig.ManualSwitchButton 未正确配置（为 null）
  • IO 设备对象已创建但 IsEmpty() 返回 true
  • IO 设备初始化时序问题：配置尚未加载时 MachineMonitor 已开始轮询

与日志的吻合度：第一次软件按钮触发时 CanAutoRun 正确拦截（说明当时回调执行了），第二次却通过——暗示 IO 状态读取存在时序不一致。

原因 2：硬件按钮切换存在信号抖动 / 短暂回弹

可能性：中高

手动/自动切换为物理旋钮或拨动开关。开关切换过程中可能产生短暂的信号回弹（bounce），导致 GetDigitalIn() 在某个轮询周期读到 true（自动）。

关键时间窗口：

  • 第一次启动尝试：16:14:40 — IO 读到手动，正确拦截
  • 第二次启动尝试：16:14:44 — 仅 4 秒后，IO 读到自动，通过检查

如果操作人员在 4 秒内操作了切换按钮又拨回自动，或者开关触点产生抖动，就有可能在这段时间窗口内被 MachineMonitor 轮询到自动信号。

原因 3：MachineMonitor 与手动/自动状态监控的竞态条件

可能性：中

MachineMonitor 内部依次执行三段 ProcessIO（启动按钮、暂停按钮、手动/自动切换）。在同一轮询周期中：

// MachineMonitor 同一轮询周期内的顺序：
1. 检查 StartButton IO → 调用 CanAutoRun()
2. 检查 PauseButton IO
3. 检查 ManualSwitchButton IO → 更新 isAutoMode

如果在第 1 步执行 CanAutoRun 时，ManualSwitchButton 的 IO 信号恰好处在切换瞬间的过渡态（或之前轮询周期中残留的高电平），则检查通过。而第 3 步才真正更新状态变量。

原因 4：IO 读取缓存 / 通信延迟

可能性：中低

GetDigitalIn() 依赖底层设备通信（如 Modbus、EtherCAT 等）。可能存在：

  • IO 驱动层缓存了上一次读取结果，未及时刷新
  • 通信延迟导致读到的状态与实际不一致
  • 多线程并发读取时，状态更新和读取之间存在竞争

原因 5：MachineStartEvent 事件路径缺少独立的手动状态检查

可能性：中低

IO 路径触发 MachineStartEvent 后，MController_MachineStartEvent（ToolBarContentVM.cs:370）直接调用 tryStart()，虽然 tryStart → Start() 内部有 CanAutoRun 检查（第826行），但 tryStart 本身未做检查。如果 Start() 内的检查也存在上述问题，则形成双重缺陷。

8. 核心缺陷总结

根因：CanAutoRun 方法中 isAuto 默认值为 true

当 ProcessIO 回调因任何原因未执行时（配置缺失、IO设备未连接、初始化时序问题），安全检查被静默绕过，返回"允许自动运行"。

这违反了 安全优先（Fail-Safe） 原则：安全检查的默认值应当是"禁止"，而非"允许"。

9. 建议修复方案

方案 A：修复 CanAutoRun 默认值（推荐）

public bool CanAutoRun(out string mesage)
{
    bool isAuto = false;           // ← 安全默认值：禁止
    bool ioChecked = false;       // ← 追踪回调是否执行
    string error = "";
    mesage = "";

    ProcessIO(SysConfig.ManualSwitchButton, (r) =>
    {
        ioChecked = true;
        isAuto = r.GetDigitalIn();
        if (!isAuto)
            error = "机台处于手动状态,不允许自动运行!";
    });

    // 未配置手动/自动按钮时，默认允许（兼容无机台型）
    if (!ioChecked)
        isAuto = true;

    mesage = error;
    return isAuto;
}

方案 B：增加 IO 信号防抖

在 MachineMonitor 中对手动/自动切换信号增加消抖逻辑，要求连续 N 次读取一致才认为状态变更有效：

// 连续3次读到同一状态才确认切换
private int _autoModeDebounce = 0;
private const int DebounceThreshold = 3;

方案 C：MController_MachineStartEvent 增加独立检查

private void MController_MachineStartEvent(string obj)
{
    // 独立安全检查（不依赖 MachineMonitor 中的检查）
    if (!mController.CanAutoRun(out var err))
    {
        commonBus.OnLog(LogType.Warning, $"IO触发启动被拦截: {err}");
        return;
    }
    // ... 原有逻辑
}

建议同时实施方案 A + C，并视硬件情况考虑方案 B。
