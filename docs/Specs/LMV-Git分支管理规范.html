LusterMotion (LMV-2026) · Git 分支管理规范

📌 版本 v1.0 📅 生效 2026-06-13 📦 lm2026-group/lmv-2026 🌿 GitFlow（在现有模型上修正执行纪律）
本规范在团队现有 GitFlow（.gitlab/issue_templates/ 已含 feature/bug/hotfix/release）基础上修正执行纪律，不引入新模型。目标：把当前 37 个分支收敛并长期维持在 15 个以内，让 master 重新成为可发布、可回滚的基准。

1 · 一句话原则

能在 3-5 天内做完合掉的就建分支做；做不完的先想怎么拆小，而不是让分支变长。功能完成即合、合完即删、master 按版本走。

团队当前的病根不是"分支建得多"，而是"分支活得太久、不及时合、合完不删"（多个分支领先 master 400+ 提交）。本规范的核心就是治这个。

2 · 分支模型总览

分支角色从哪拉合并去向生命周期
master发布主干，永远代表现场在跑、可回滚的版本—仅接受 release/*、hotfix/*永久
develop集成主干，日常开发汇集点master→ release/*永久
feature/*新功能、重构develop→ develop≤ 1-2 周
bugfix/*非紧急缺陷修复develop→ develop≤ 1 周
release/*发版前回归与版本定版develop→ master 且回合 develop发版期间
hotfix/*现场紧急修复master→ master 且回合 develop数小时-数天
customer/*长期维护的客户定制变体develop/master按需双向同步随客户项目
一次性客户交付不要建长期分支，做完合回 develop 即删；只有需要长期独立维护的变体才用 customer/*。

3 · 要不要建分支？

默认都建分支，禁止直接向 develop / master push。 区别只在分支大小与寿命：

改动类型做法
新功能 / bug 修复 / 重构（哪怕只改几个文件）建分支 → MR 合入 develop
改文案 / 常量 / 注释等几行琐碎改动轻量分支 当天合掉，可不开 issue
直接 push 到 develop / master禁止 靠分支保护强制堵住（见 §9）
关键不是"有没有分支"，而是分支必须小：1 个分支 = 1 个功能 = 几天内 = 几十个提交以内。大功能必须拆成可独立合并的小步。例：音圈电机 → 先合"基础框架"，再合"DH 协议"，再合"钧舵协议"，每步几天内合掉，而不是憋一个 +300 提交的巨型分支。

4 · 分支命名规范

格式：<类型>/<模块或issue号>-<简短描述>，全小写，词间用连字符 -。

✅ 推荐

feature/vcm-junrudder-softlanding
feature/issue-42-pdca-upload
bugfix/issue-108-alarm-state-stuck
hotfix/hive-timezone-offset
release/v3.18.0
customer/byd-mes-adapter
customer/goer-ar-station

❌ 禁止（均为当前仓库真实反例）

0604_t                 # 纯日期/缩写，无语义
0508_proj_byd          # 日期前缀
Gly0528-1              # 人名+日期
zhyu                   # 个人镜像分支
feature/TEST-2026...   # 测试垃圾分支
  • 客户定制统一加客户前缀：feature/byd-*、customer/goer-*。
  • 能关联 issue 的，分支名带 issue 号，便于追溯。
  • 禁止个人镜像分支（如 zhyu ≈ develop）——用本地分支即可，不要推到远程。

5 · 合并时机与方向 最重要

5.1　feature / bugfix → develop

  • 功能做完 + 自测通过 + 评审通过 → 立刻合，不要攒。
  • 大功能拆小步，每步独立合并。
  • feature 分支每周至少同步一次 develop（merge 或 rebase），把冲突消化在平时，避免憋到最后爆炸式冲突。

5.2　develop → master（发版，当前完全缺失的环节）

  • 按发版节奏（每次现场发版 / 每个迭代结束）执行。
  • 经验证的 develop → 拉 release/vX.Y.Z 定版回归 → 合入 master → 打 Tag。
  • master 永远 = 现场在跑、可回滚的版本。

5.3　hotfix → master + develop

  • 现场急修从 master 拉 hotfix/*，修完同时合回 master 和 develop（及进行中的 release），避免下次发版又把同一 bug 带回来。

合并方向速查

feature / bugfix  ──►  develop
develop  ──►  release/*  ──►  master  ──►  tag
hotfix  ──►  master  (+ 回合 develop)

6 · 合并前置条件（MR 检查清单）

向 develop / master 合并的 MR，必须满足：

  • 已 merge/rebase 最新目标分支，冲突已解决
  • 本地 dotnet build LMV-2026.sln 通过
  • 功能自测通过（必要时附测试/验证说明）
  • 至少 1 人 Code Review 通过（可挂本仓库的代码审查流程为门禁）
  • GitLab 流水线（CI）绿
  • 已关联对应 issue
  • 合并后勾选"删除源分支"
合并方式：feature/bugfix → develop 用普通 merge（保留历史），历史过碎时用 squash；release/hotfix → master 用 merge + 打 Tag。

7 · 发版流程（develop → master）

  1. 冻结 develop，确认目标范围已全部合入。
  2. 从 develop 拉 release/vX.Y.Z，做最后回归、修订版本号/变更记录（只允许 bug 修复，不加新功能）。
  3. release/* 合入 master。
  4. 在 master 打产品级 Tag。
  5. release/* 回合 develop（带上定版期间的修订），随后删除 release 分支。
⚠️ 仓库用 MinVer + 每项目包级 Tag（{ProjectName}-v{version}，如 Luster.Prism-v1.2.3）。产品整体发版的 Tag 请用独立前缀（如 app-v3.18.0 / release-v3.18.0），避免与 MinVer 的包级 Tag 混淆。

8 · 日常纪律

  • 合完即删：MR 合并时勾选删除源分支；GitLab 里设为默认勾选。
  • 每周同步：未合并的 feature 每周至少同步一次 develop。
  • 月度巡检：每月清理 ①已合并分支 ②>30 天无活动分支 ③测试/演示垃圾分支。
# 列出已并入 develop 可删除的分支
git branch -r --merged origin/develop | grep -v -E 'HEAD|master|develop'
# 按最后提交时间列出全部分支（找陈旧分支）
git for-each-ref --sort=committerdate refs/remotes/origin \
  --format='%(committerdate:short) %(authorname) %(refname:short)'

统一 Git 署名：同一人勿用多标识（JZ/jiezhu、gx1555/郭旭、zhangyu/zhyu），统一 user.name / user.email，便于贡献统计与责任追溯。

9 · GitLab 分支保护与合并设置（管理员配置一次）

Settings → Repository → Protected branches

  • master、develop 设为保护分支：
  • Allowed to push：No one（禁止直接 push）
  • Allowed to merge：Maintainers（或指定角色）

Settings → Merge requests

  • 勾选 Enable "Delete source branch" by default
  • 开启 Squash commits 选项（可选）
  • 设置 Approvals required ≥ 1

Settings → Repository → Push rules（可选，企业版）

用正则强制分支命名：

^(master|develop|(feature|bugfix|hotfix|release|customer)/.+)$

场景怎么做
